# DX-2 / DX-3 / DX-12 — Consolidated decide-result type and command path

**Finding IDs:** DX-2, DX-3, DX-12
**Impact level:** Breaking — affects any code that uses `DecisionResult<TEvent>`, `DecideAndAppendAsync`, or the standalone `AddAlbertoStore(IServiceCollection, object, Assembly)` overload.

---

## What changed

### 1. Single blessed decide-result type: `Decision` / `Decision<T>`

`DecisionResult<TEvent>` (in `Alberto.Dcb`) is now **obsolete** and will be removed in a future version.
Use `Decision` (for void commands) or `Decision<T>` (when the decision carries a return value) from the `Alberto.Dcb.Commands` package.

These types live in `namespace Alberto.Dcb` and are already the types used by `AlbertoStore.Handle(…).Decide(…)`, so no extra `using` statement is needed.

| Before | After |
|---|---|
| `DecisionResult<TEvent>.Success(evt)` | `Decision.Succeed(evt)` |
| `DecisionResult<TEvent>.Failure("reason")` | `Decision.Fail(Problem.Create("code", "reason"))` |
| `result is DecisionResult<TEvent>.Ok ok` | `result.IsSuccess` / `result.Events` |
| `result is DecisionResult<TEvent>.Fail fail` | `result.IsError` / `result.Problems` |
| `result.EnsureSuccess()` | `result.Events` (check `result.IsSuccess` first) |

### 2. `DecideAndAppendAsync` moved from `IEventStoreBackend` to `IEventStore`

The extension method now lives in `Alberto.Dcb.Commands` and extends `IEventStore` instead of `IEventStoreBackend`. This makes it discoverable wherever `IEventStore` is injected, without requiring a downcast to the backend.

The signature also changed:
- Decision function type: `Func<TState, DecisionResult<TEvent>>` → `Func<TState, Decision>`
- Event mapper type: `Func<TEvent, IEventToPersist>` → `Func<IEvent, IEventToPersist>`
- Return type: `Task<DecisionResult<TEvent>>` → `Task<Result>`
- Type parameter: generic `<TState, TEvent>` → `<TState>` only (event type is no longer part of the boundary)

| Before | After |
|---|---|
| `backend.DecideAndAppendAsync<TState, TEvent>(…)` | `eventStore.DecideAndAppendAsync<TState>(…)` |

### 3. `AddAlbertoStore` chains from the builder

A new builder-chaining overload makes `AlbertoStore` registration discoverable alongside the rest of the module configuration:

```csharp
services.AddAlberto("orders", builder => builder
    .WithPostgres(options => …)
    .AddAlbertoStore(typeof(OrderCreated).Assembly)   // ← new primary form
    .WithControlLoop()
);
```

The old standalone overload `services.AddAlbertoStore(moduleKey, assembly)` is now `[Obsolete]` and will be removed in a future version.

---

## Why

The library shipped three overlapping result types and two-and-a-half separate command paths:

- `DecisionResult<TEvent>` — abstract record, pattern-matched, event-typed, string-based failure
- `Decision` / `Decision<T>` — struct, `IsSuccess`/`IsError`, carries `Problem` list
- `Result` / `Result<T>` — struct, `IsSuccess`/`IsFailure`, carries `Problem` list (pipeline output)

Having three types for the same concept confused integrators about which to use. `Decision` / `Decision<T>` are the correct types for the "should we append?" question; `Result` / `Result<T>` model the outcome of the persist step. `DecisionResult<TEvent>` had overlap with both and is now redundant.

Similarly, `DecideAndAppendAsync` on `IEventStoreBackend` was invisible to consumers who inject `IEventStore`, and the standalone `AddAlbertoStore` call was disconnected from the `AddAlberto` builder.

---

## Migration guide

### If you use `DecisionResult<TEvent>` in your domain logic

```csharp
// BEFORE
public static DecisionResult<IEvent> Create(…)
{
    if (already exists) return DecisionResult<IEvent>.Failure("Order already exists");
    return DecisionResult<IEvent>.Success(new OrderCreated(…));
}
```

```csharp
// AFTER
public static Decision Create(…)
{
    if (already exists) return Decision.Fail(Problem.Create("already-exists", "Order already exists"));
    return Decision.Succeed(new OrderCreated(…));
}
```

### If you call `DecideAndAppendAsync`

```csharp
// BEFORE  (on IEventStoreBackend)
var result = await backend.DecideAndAppendAsync<OrderState, IEvent>(
    boundary,
    evolver,
    state => state.Exists
        ? DecisionResult<IEvent>.Failure("Already exists")
        : DecisionResult<IEvent>.Success(new OrderCreated(…)),
    @event => new EventToPersist { … },
    ct);

if (result.IsFailure) { … }
```

```csharp
// AFTER  (on IEventStore)
var result = await eventStore.DecideAndAppendAsync<OrderState>(
    boundary,
    evolver,
    state => state.Exists
        ? Decision.Fail(Problem.Create("already-exists", "Already exists"))
        : Decision.Succeed(new OrderCreated(…)),
    @event => new EventToPersist { … },
    ct);

if (result.IsFailure) { … }
```

### If you call `services.AddAlbertoStore(moduleKey, assembly)`

```csharp
// BEFORE  (standalone, disconnected from builder)
services.AddAlberto("orders", builder => builder.WithPostgres(…));
services.AddAlbertoStore("orders", typeof(OrderCreated).Assembly);
```

```csharp
// AFTER  (chained from builder)
services.AddAlberto("orders", builder => builder
    .WithPostgres(…)
    .AddAlbertoStore(typeof(OrderCreated).Assembly)
);
```

### Primary command path (no change needed)

If you already use the `AlbertoStore.Handle(…).Validate(…).Load(…).Decide(…).Persist(…)` fluent pipeline, **no migration is required** — that path is unchanged and remains the primary recommendation.
