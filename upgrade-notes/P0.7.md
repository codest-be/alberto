# P0.7 — Inline EF projection retry exhaustion now throws `InlineProjectionExhaustedException`

## What changed

`DeclaredEfInlineProjection` and `EfInlineProjection` both retry a failed commit up to 5 times when a concurrency conflict (`DbUpdateConcurrencyException` or unique-violation `23505`) is detected.

**Before:** after all retries were exhausted the original `DbUpdateConcurrencyException` or `DbUpdateException` propagated out of `ProcessAsync`. There was no log entry and no way for the caller to distinguish "first-attempt failure" from "all 5 retries exhausted".

**After:** on exhaustion a `Critical`-level log entry is emitted (if a logger is injected), and the exception is wrapped in `InlineProjectionExhaustedException` which carries `ProcessorId`, `Attempts`, and `DocumentCount` for structured alerting. The original exception is available via `InnerException`.

## Why

When exhaustion occurs the events are already durable in the event store but the inline projection view is diverged. Without an explicit signal, operators have no way to know that a replay is required; the divergence is silent until a consumer reads stale data.

## Migration

**Callers catching `DbUpdateConcurrencyException` on the inline-projection path must be updated.**

```csharp
// Before
try
{
    await eventStore.AppendAsync(...);
}
catch (DbUpdateConcurrencyException ex)
{
    // handled inline-projection failure
}

// After
try
{
    await eventStore.AppendAsync(...);
}
catch (InlineProjectionExhaustedException ex)
{
    // Exhaustion: ex.ProcessorId, ex.Attempts, ex.DocumentCount available.
    // Schedule an async replay for the affected projection.
    logger.LogCritical("Projection {Id} diverged — replay required", ex.ProcessorId);
}
catch (DbUpdateConcurrencyException ex)
{
    // Single-attempt failure that did not trigger the retry path
    // (e.g., external-transaction mode where ownsTransaction == false).
}
```

The exception type is defined in `Alberto.Dcb.EntityFramework.Inline.InlineProjectionExhaustedException`.

## Optional: inject a logger

To receive the `LogCritical` entry, resolve the logger from DI and pass it during construction. `EfConsumerBuilderExtensions` (not yet updated — see cross-file note) should forward `sp.GetService<ILogger<DeclaredEfInlineProjection<TEntity, TDbContext>>>()` to the constructor. Until then, pass the logger manually if you construct the projection yourself.
