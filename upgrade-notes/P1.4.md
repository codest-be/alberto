# P1.4 — Startup tenancy-mode consistency check

## What changed

`PostgresBuilderExtensions.WithPostgres()` now calls `PostgresMigrator.ValidateTenancyMode()`
at startup. It queries `information_schema.columns` to check whether the `tenant_id` column
exists in `alberto_events` and compares that against the configured tenancy mode
(`.WithTenancy()` present or absent).

If the configured mode does not match the actual schema shape, startup fails with a clear
`InvalidOperationException`.

## Why

The single- and multi-tenant migration sets journal under different script names. Running the
wrong set against an existing DB executes "unapplied" scripts that `CREATE OR REPLACE` stored
functions with the wrong signatures (e.g., missing `tenant_id` parameter). The DB then silently
accepts data in the wrong format until an unrelated call fails with a cryptic Postgres error.
This check catches the mismatch before any harm is done.

## Impact

**May cause startup failures for existing deployments that have a tenancy mismatch.**

If you see this error at startup:
```
Alberto tenancy mismatch (schema 'public'): the application is configured for multi-tenant mode
but the database was migrated in single-tenant mode (alberto_events.tenant_id is absent).
```

Fix by either:
1. Changing the application configuration to match the DB (remove `.WithTenancy()` if single-tenant)
2. Dropping the schema and re-running the correct migration set
3. Manually applying the missing migration scripts for the intended mode

Do **not** disable this check — the stored functions will not behave correctly if the modes
are mismatched.

## Note for AutoMigrate=false deployments

The check runs even when `AutoMigrate` is false. The expectation is that if you manage
migrations manually, the DB must be fully set up before the application starts.
